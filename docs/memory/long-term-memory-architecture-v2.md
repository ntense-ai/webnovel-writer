# Current Long-Term Memory Architecture

## Document Scope

This document describes only the long-term memory architecture implemented in the repository and actually consumed by the main writing pipeline.

It excludes historical refactoring plans and idealized blueprints. The sole criterion is whether a feature exists in the current code and is integrated into the main pipeline.

## Summary

The actual long-term memory implementation:

- Uses `.webnovel/memory_scratchpad.json` as a long-term semantic-memory cache
- Uses `index.db`, `summaries/`, and `state.json` for recent state and historical evidence
- Uses `MemoryOrchestrator` to assemble working / episodic / semantic layers
- Exposes the result through `ContextManager`, `extract_chapter_context.py`, and `MemoryContractAdapter`

This is a working data pipeline, but not yet a fully independent memory subsystem.

## Core Boundaries

### Already in the Main Long-Term Memory Pipeline

- `scripts/data_modules/memory/schema.py`
- `scripts/data_modules/memory/store.py`
- `scripts/data_modules/memory/writer.py`
- `scripts/data_modules/memory/orchestrator.py`
- `scripts/data_modules/memory/bootstrap.py`
- `scripts/data_modules/memory/compactor.py`
- `scripts/data_modules/memory_contract_adapter.py`
- `scripts/memory_cli.py`
- `scripts/data_modules/context_manager.py` injection of `long_term_memory`

### Still Separate or Adjacent Capabilities

- `.webnovel/project_memory.json`
- Project-experience memory produced by `/webnovel-learn`
- The `memory` section in `ContextManager`

These are read alongside context but are not the same as the `memory_scratchpad.json` long-term memory pipeline.

## Current Architecture

```text
Chapter results / review artifacts
        │
        ▼
MemoryWriter
        │
        ├── Write memory_scratchpad.json
        ├── Maintain active/outdated/contradicted/tentative
        └── Trigger compaction and conflict checks

state.json / index.db / summaries/ / memory_scratchpad.json
        │
        ▼
MemoryOrchestrator
        │
        ├── working_memory
        ├── episodic_memory
        ├── semantic_memory
        └── long_term_facts / active_constraints / warnings / stats

        ▼
ContextManager
        │
        ├── long_term_memory section
        ├── extract_chapter_context.py
        └── MemoryContractAdapter / memory CLI

        ▼
webnovel-write / review / query / other consumers
```

## Data Layers

### 1. Working Memory

Not stored separately; assembled transiently at runtime, mainly from:

- The current chapter outline
- Recent chapter summaries
- Protagonist state, plot threads, and pending disambiguations in `state.json`

Generated by `MemoryOrchestrator._build_working_memory()`.

### 2. Episodic Memory

Currently comes mainly from recent structured evidence in `index.db`, not an independent general historical-retrieval system.

Main sources:

- Recent state changes
- Recent relationship changes
- Recent appearances

Generated by `MemoryOrchestrator._build_episodic_memory()`. It emphasizes recent evidence, not semantic recall across the entire database.

### 3. Semantic Memory

The core long-term memory store is `.webnovel/memory_scratchpad.json`.

`ScratchpadManager` reads/writes it, storing items in category buckets:

- `character_state`
- `story_facts`
- `world_rules`
- `timeline`
- `open_loops`
- `reader_promises`
- `relationships`

All memory items use the `MemoryItem` structure, with core fields:

- `id`
- `layer`
- `category`
- `subject`
- `field`
- `value`
- `payload`
- `status`
- `source_chapter`
- `evidence`
- `updated_at`

Supported statuses:

- `active`
- `outdated`
- `contradicted`
- `tentative`

## Write Pipeline

### 1. Chapter Results Enter `MemoryWriter`

After committing a chapter, the main writing pipeline passes structured results to `MemoryWriter.update_from_chapter_result()`.

Implemented write sources:

- `state_changes`
- `entities_new`
- `relationships_new`
- `chapter_meta.hook`
- `memory_facts`

`memory_facts` provides deeper structured mapping and currently supports:

- `timeline_events`
- `world_rules`
- `open_loops`
- `reader_promises`

### 2. `ScratchpadManager` Deduplicates and Consolidates State

Core rules of `ScratchpadManager.upsert_item()`:

- Compute a deduplication key using category-specific primary-key rules
- Downgrade the old value with the same key to `outdated`
- Write the new value as the current valid item
- Retain old values for audit and rollback

`schema.py` centrally defines primary-key rules for each category, for example:

- `character_state`：`subject + field`
- `relationship`：`subject + field`
- `world_rule`：`subject + field`
- `open_loop`：`subject`

### 3. Compact When Thresholds Are Exceeded

`ScratchpadManager.save()` invokes `compactor.py` once thresholds are reached.

Current compaction strategies:

- Retain only the latest `outdated` item per key
- Remove resolved foreshadowing
- Merge old timeline entries into summary-like `story_fact` items
- If still over the total limit, truncate globally by status and freshness

### 4. Backfill Existing Projects

`memory bootstrap` backfills initial long-term memory from existing `index.db` and `summaries/`.

Currently supported backfill content:

- Current character states
- Historical state changes
- Recent relationships
- Foreshadowing blocks in summaries

## Read and Orchestration Pipeline

### 1. `MemoryOrchestrator` Assembles a Unified Pack

`MemoryOrchestrator.build_memory_pack()` is the unified long-term memory read entry point.

It performs four tasks:

1. Build `working_memory`
2. Build `episodic_memory`
3. Read `active` items from `memory_scratchpad.json`
4. Filter, apply limits, and add warnings/statistics

Core output fields:

- `working_memory`
- `episodic_memory`
- `semantic_memory`
- `long_term_facts`
- `active_constraints`
- `recent_changes`
- `warnings`
- `stats`

Specifically:

- `semantic_memory` and `long_term_facts` currently contain the same directly injectable long-term semantic facts
- `active_constraints` mainly extracts `world_rule` and `open_loop`
- `warnings` mainly exposes memory conflicts

### 2. Current Filtering Rules

`semantic_memory` is lightly filtered before injection rather than included in full.

Current filtering criteria:

- Whether an item's `subject / field / value` appears in the chapter outline
- Whether its source chapter falls within the configured window

Then truncate to budget. `budget.py` and configuration jointly control the budget.

## Consumer Layer

### 1. `ContextManager`

`ContextManager` remains the overall writing-context assembler.

When `context_use_memory_orchestrator=true`, it:

- Calls `MemoryOrchestrator.build_memory_pack()`
- Injects the result into the `long_term_memory` section
- Assembles the final context with `reader_signal / genre_profile / writing_guidance / plot_structure`

Thus memory is integrated into ContextManager, not a complete replacement for it.

### 2. `extract_chapter_context.py`

The prewrite context script extracts key sections from `ContextManager`, already including:

- `reader_signal`
- `genre_profile`
- `writing_guidance`
- `plot_structure`
- `long_term_memory`

Long-term memory therefore reaches the main writing context rather than remaining in an isolated experimental script.

### 3. `MemoryContractAdapter`

`MemoryContractAdapter` is a thin external adapter.

It wraps existing modules in a unified interface providing:

- `commit_chapter()`
- `load_context()`
- `query_entity()`
- `query_rules()`
- `read_summary()`
- `get_open_loops()`
- `get_timeline()`

The memory pipeline has a stable interface, while underlying storage still reuses existing `state / index / scratchpad / summaries`.

### 4. CLI

Long-term memory CLIs fall into two groups:

- `webnovel.py memory ...`
- `memory_cli.py`

Common commands:

- `memory stats`
- `memory query`
- `memory dump`
- `memory conflicts`
- `memory bootstrap`
- `memory update`

## Storage Responsibilities

### `state.json`

Owns runtime state, not accumulated long-term knowledge.

Primarily stores:

- Protagonist snapshot
- Progress
- Plot threads
- Pending disambiguations

### `index.db`

Owns structured historical evidence.

When reading `episodic_memory`, long-term memory primarily obtains:

- State changes
- Relationships
- Appearances
- Some reader-retention and review data

### `summaries/`

Owns chapter summaries and recent writing context.

It has two roles in the long-term memory pipeline:

- Provides recent summaries for `working_memory`
- Backfills foreshadowing-type open questions during `bootstrap`

### `memory_scratchpad.json`

Owns the long-term semantic-memory cache, the current primary source for long-term memory.

### `project_memory.json`

Owns accumulated project experience/learning. It remains a separate side channel, not merged with `memory_scratchpad.json`.

## Implemented Capabilities

- Persistent long-term memory reads/writes
- Unified schema, status enumeration, and bucket structure
- Conflict detection and simple status downgrading
- Compactor to prevent unbounded scratchpad growth
- Long-term memory injection into the main writing context
- CLI query, backfill, and manual-update entry points
- Stable external interface via `MemoryContractAdapter`

## Current Boundaries and Limitations

### 1. Not a Fully Independent Memory Runtime

Still depends on:

- `ContextManager` for final assembly
- `index.db` for recent historical evidence
- `state.json` for runtime snapshots

### 2. `episodic_memory` Emphasizes Recent Evidence, Not Full Historical Recall

It is a recent structured-evidence layer, not a unified book-wide semantic-recall system.

### 3. `semantic_memory` Is Still a JSON Scratchpad

There is no separate long-term semantic vector layer or graph-database layer.

### 4. `project_memory.json` Is Not Unified with the Main Memory Pipeline

Project-experience memory and long-term story memory remain parallel data sources.

### 5. Conflict Resolution Uses Lightweight Rules

Currently limited mainly to:

- Primary-key deduplication
- Old-value downgrading
- Conflict statistics

No heavier cross-chapter semantic-adjudication process exists yet.

## Conclusion

Long-term memory has moved from proposal discussion to a working architecture. Its actual positioning is:

- Integrated into the main writing pipeline
- Equipped with persistence, orchestration, consumers, and operational entry points
- Still built on the existing `ContextManager + state/index/summaries` ecosystem

This document therefore describes only the current architecture.

Historical plans have been removed. Future evolution should get a new, separate specification based on the actual code at that time.
